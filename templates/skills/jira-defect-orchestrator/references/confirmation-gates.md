# 检查点与决策确认

## 检查通过与人工确认

G1～G5 保留各阶段需要形成的证据和授权检查。到达检查点不等于必须暂停；用户明确要求逐阶段确认时按该要求执行。

| 检查点 | 自主继续的条件 | 需要用户决定的情况 |
| --- | --- | --- |
| `G1 根因检查` | 证据解释触发条件、实际路径和错误机制，没有影响修复方向的关键未知 | 无法自主补齐的关键证据、根因分歧或新增影响需要外部信息或取舍 |
| `G2 方案检查` | 已获实现授权；方案已明确，或最小修复恢复既有约定且不新增行为、兼容或数据风险 | 缺少实现授权；多个实质方案；范围、契约、数据处理或风险变化 |
| `G3 Jira 变更` | 对应 issue、动作与目标已有明确且仍有效的授权 | 评论、状态或指派动作尚未授权，或超出原授权范围 |
| `G4 验证检查` | 约定的必要验证已通过，证据覆盖当前改动与验收 | 需要改变验收、用替代证据接受缺口或处理新增风险 |
| `G5 收尾检查` | 收尾条件满足，且最终评论、状态或关闭动作分别已有对应授权 | 尚未授权的最终动作，或关闭、观察、退回的取舍发生变化 |

调查和验证失败时，先在已授权范围内继续补证或修复。用户认可不能替代证据，也不能使失败或未执行的检查变为通过。诊断任务可以报告根因与修复建议，但不能因此进入代码修改。

## 授权复用

- 根据当前任务与已有对话理解授权，不要求用户必须在决策卡之后再次回复。
- “按这个方案修复”覆盖该方案范围内的实现、验证与按需审查。“修复这个缺陷”允许在根因明确且恢复既有约定的范围内完成最小修复。
- “继续”只延续上一条已明确展示的动作与范围；含糊时只澄清真正影响下一步的部分。
- 本地修复授权不自动包含 Jira 评论、move、assign、关闭、commit、push、MR、部署或发布；对应动作已有明确授权时直接复用，不重复询问。
- 条件授权仅在条件被实际证据满足时生效；例如“必要验证通过后关闭该 issue”不能在验证失败或关键项未执行时执行。
- 根因检查通过不授权将 issue 自动推进到进行中。确认根因、方案或验证结果，也不默认授权把它们发布为 Jira 评论。
- 用户只确认一部分，就只执行该部分。补充问题本身不构成新的确认；答案未改变已确认内容时，不重开已经完成的确认。

## 何时暂停

只在下一步依赖尚未解决的决定、缺失信息或授权时暂停该部分工作，并继续不依赖它的已授权工作。例如，Jira 评论未授权或同步失败，不阻断已有证据足够的本地修复；若用户明确要求先流转再实施，则保留该依赖。

G1 与 G2 的问题可以在事实足够、没有依赖缺口时合并展示。不要为了阶段完整性分别索要“根因认可”和“方案认可”。

## 展示方式

检查通过时用一句话报告结论、依据和下一动作，例如：

> 根因已由日志与代码交叉验证，最小修复恢复原有状态清理约定；按本次修复授权继续实现和回归验证。

确需用户决定时，仅展示：

1. 需要决定的一件事，以及它为何影响结果；
2. 推荐做法、证据和主要代价；存在真实替代时再给选项；
3. 等待该决定的具体动作，以及能继续推进的独立工作。

不强制表格、A/B/C、固定行数或重复的回复提示。支持提问工具时使用它；否则用一句清晰问题收尾。

用户追问时直接回答。只有新证据改变了决定对象或选项时才更新决策说明；不要每次重发完整卡片。Jira 写入准备与本地推进的状态分别报告。
