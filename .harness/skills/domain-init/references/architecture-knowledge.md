# 架构知识扫描与验收

选中 K1，或增强项涉及当前架构说明时使用。记录当前实现；待实施方案留在任务文档中。
只调查已确认的作用域和主题，按 `output-formats.md` 归属、引用与合并产物。

## 扫描顺序

1. **定位仓库与入口**：识别单仓、monorepo 或多仓；读取各目标仓库的 manifest、构建配置、
   启动入口与已有文档。分别确认职责、技术栈、共享配置和依赖集成方式；根项目记录跨项目关系，
   子项目记录自身实现，跨项目通过链接关联。
2. **追踪结构与依赖**：沿入口和代表性调用链核对模块、分层、组装位置与依赖方向。
   区分源码调用、包/构建依赖与进程间通信；命名和目录只能提供线索，结论须核对代码与配置。
3. **追踪通信与流程**：从已确认范围内的关键入口追到结果及失败分支，核对跨边界调用、
   消息或事件定义、状态变化及恢复处理。高优先项深入边界与例外，其余按已确认深度采样。
4. **映射已有文档**：将发现对应到已有主题和缺口，形成目标文件、依据及待确认事项，交回
   Phase 2/3 review；跨仓调用链的发现不扩大对子项目的写入授权。

## 按需覆盖的内容

以下是内容检查项，不是固定章节或文件清单。已有文档能承接时直接更新；简单项目可合并，
没有触点的主题省略。DDD 仅在代码或已确认约定支持时展开。

| 主题 | 应回答的问题 | 可复用的文档位置示例 |
|------|--------------|----------------------|
| 项目与结构 | 项目做什么；各仓库/模块、入口、技术栈、分层、依赖方向与集成方式是什么 | project.md、architecture.md |
| 组件与归属 | 组件负责和不负责什么；边界依据是什么；新功能按什么判据归属 | architecture.md；内容较多时 components.md / modules.md |
| 通信与契约 | 谁调用谁；同步/异步、协议或机制、接口/消息定义、用途、所属模块和代码入口是什么 | architecture.md；按需拆分 communication-patterns.md / interfaces.md |
| 关键流程 | 从触发到结果经过哪些组件和状态；关键失败、超时、重试、取消或恢复在何处处理 | 现有业务专题；按需创建流程文档 |
| 开发与交付 | 在哪里运行构建、测试和发布；哪些配置或脚本定义环境、版本与依赖更新方式 | development.md、testing.md、已有发布文档 |

组件归属在存在多种落点时使用简短决策表，列出任务类型、所属组件与边界依据。
现有代码只能证明边界和依赖；历史划分理由遵循 Docs 的证据标记要求，不反推为已确认决定。

通信检查由实际触点触发，覆盖 HTTP/RPC、队列、IPC、CLI/SDK 调用、回调或事件。
接口清单优先链接已有协议、schema、路由或公开头文件；缺少导航时仅补充定位表，字段按机制裁剪
为方法/命令/路径/topic、用途、调用方与接收方、所属模块和定义位置，避免复制完整定义。
未发现的超时或恢复机制记为扫描范围内的缺口，不补写理想行为。

## 图表与导航

- 模块或跨仓关系难以用短文解释时，用 Mermaid flowchart/graph 表达职责与依赖方向；
  跨组件交互复杂时用 sequenceDiagram，必要时补充状态图。简单关系用文字或表格。
- 图中参与者、调用方向和状态须与实现及正文一致。显示文本加引号；classDiagram 使用合法类
  标识符，不将带 `::` 的命名空间直接用作类标识符。
- 专题之间用相对链接关联；文档索引注明用途和读取场景，AGENTS 只链接实际存在的文档。

## 完成检查

- 读者能找到入口、职责边界、依赖方向与相关代码，能判断新增功能的归属。
- 已选且有触点的通信与流程说明包含调用双方、关键状态和失败路径；无法追踪的边界已列明。
- 图表、正文和接口导航使用一致名称与方向，关键结论可定位到证据。
- 已覆盖主题能指向目标文档；未覆盖范围、推断、待确认事项和未验证行为进入报告。
