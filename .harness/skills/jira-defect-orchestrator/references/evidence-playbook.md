# 运行态缺陷证据手册

## 1. 时间规范化

- 把相对时间转为 `YYYY-MM-DD HH:mm:ss ±offset`。
- 日志查询使用 RFC 3339；Asia/Shanghai 示例：`2026-08-03T11:44:00+08:00`。
- 规范化平台环境名（如 `fat/FAT`、`prod/PRO`），同时保留原始值；不能只靠大小写映射证明两个平台指向同一实体。
- 默认窗口为事件前 10 分钟到后 20 分钟。
- 只有在环境、应用、镜像和时区已经核对后才扩大窗口。
- 区分事件发生时间、日志采集时间、数据库 create/update 时间和客户端展示时间。

## 2. 证据矩阵

| 类别 | 要回答的问题 | 首选证据 |
|---|---|---|
| Jira | 用户做了什么、何时发生、期望与实际是什么 | 描述、附件、评论、测试环境 |
| 部署 | 哪个版本实际处理请求 | 部署平台的应用详情、镜像、commit |
| 日志 | 请求走过哪些分支、输入与输出是什么 | trace/request/order 标识串联的事件 |
| 数据 | 最终写入了什么、后续读取了什么 | 带业务键与时间范围的只读查询 |
| 代码 | 为什么会产生该日志和数据 | 线上 commit 的入口、计算、DAO/Mapper |
| 验证 | 修复是否阻止原症状再次发生 | 回归测试、编译、smoke、red-green |

根因至少由两类独立证据支持。单条 ERROR 日志、单行可疑代码或单条异常数据都不能单独证明根因。

## 3. 日志收敛顺序

1. 用时间窗和症状关键词找到锚点事件。
2. 提取 traceId、requestId、orderId、messageId 或脱敏 userId。
3. 用锚点标识查询入口、核心计算、下游调用和持久化日志。
4. 对齐同一标识的时间顺序，标注缺失环节。
5. 只保留支撑判断的最小日志片段，不复制整段日志。

排查历史问题时优先查询日志归档或集中日志平台，而不是反复刷新当前 Pod。

日志工具报告没有可扫描文件时，不能写成“关键词没有命中”。无结果时先核对环境、app/cluster、镜像和时区，再扩大一次窗口；仍无结果要明确区分“没有匹配事件”和“没有可扫描文件”。

## 4. Apollo 环境对齐

- 先从代码或部署配置确认项目接入 Apollo 以及实际 `app.id`。
- 部署平台 `clusterId` 与 Apollo `clusterName` 是不同概念；通过 `app.id`、部署配置和 envclusters 核验映射，不能按名称猜测。
- Apollo 必须与事发 部署平台 应用属于同一规范环境，同时保留两个平台返回的原始环境名。
- 认证不完整时记录访问阻塞，不猜认证头，也不复制其他环境的配置作为事实。

## 5. 数据库只读查询约束

### 允许

- `SELECT`、`SHOW`、`DESCRIBE`、普通 `EXPLAIN`
- 精确主键/业务键查询
- 有索引字段和短时间范围的状态查询
- 小范围 `COUNT` 或分组，用于判断影响面

### 禁止

- `INSERT`、`UPDATE`、`DELETE`、`REPLACE`、DDL、存储过程、事务控制
- `EXPLAIN ANALYZE` 等会实际执行目标查询的变体
- `FOR UPDATE`、显式锁、临时表、导出文件
- 多语句、注释绕过、动态拼接用户输入
- 无条件 `SELECT *`、无 `LIMIT` 的明细查询、跨库大范围扫描

### 查询模板

```sql
SELECT <必要列>
FROM <已由代码或 Mapper 确认的表>
WHERE <tenant_or_owner_key> = ?
  AND <business_key> = ?
  AND <time_column> BETWEEN ? AND ?
LIMIT 100;
```

- 先用代码/Mapper 确认表和列，不猜表名。
- 参数来自 Jira、日志或前一步查询；不要拼接不受信任的输入。
- 精确查询使用主键/业务键；范围查询同时带租户/owner 与索引时间范围。
- 输出只保留支持判断的字段，并脱敏账号、手机号、邮箱、token、密钥和完整内部 ID。

## 6. 凭据处理

- 不在命令参数中直接放数据库密码。
- 不打印 Apollo 的 secret、password 或完整 JDBC URL。
- 数据库身份必须由服务端授予只读权限；无法确认时不连接。
- 平台支持时启用 TLS；设置 statement timeout，避免排障查询长期占用连接或扫描资源。
- 如客户端必须使用临时配置文件：创建在系统临时目录、权限设为 `0600`、使用后立即删除。
- 不把凭据写入仓库、Jira、MR、测试报告或会话产物。
- 最终只说明“认证成功/失败”和脱敏后的 host、database、read-only 身份信息。

## 7. 根因陈述模板

```text
触发条件：
实际路径：
错误机制：
持久化/外部结果：
用户可见影响：
证据：日志 / 数据 / 代码
反证与边界：
```

若任一关键环节缺证据，将结论标记为“候选根因”，并列出最小补证动作。

## 8. 缺证据时的降级

- **部署平台 无日志**：完成一次环境、部署和时间校准及一次合理扩窗后，保留日志缺口，不再无边界扩大查询。
- **Apollo 未接入或无权限**：记录“配置未验证”，不能把默认值或其他环境配置写成事发事实。
- **数据库不可达**：日志能证明实际路径、代码能独立证明确定性机制时，可形成有边界的根因；否则保留为候选根因。
- **多个子仓库都可能是 owner**：先用路由、类名、topic、镜像或调用链收敛 owner；未定位前不修改代码。
- **MR 目标分支无法可靠识别**：保留脚本返回的候选和置信度，先让开发者选择，不创建修复分支或执行交付。
