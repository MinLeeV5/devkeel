# Jira 缺陷处理 Playbook

## 怎么使用这份手册

从当前阶段往下读，不需要一次加载全部细节。每个阶段只回答四件事：

- 这一阶段要解决什么问题
- 必须完成哪些动作
- 什么结果代表阶段完成
- 什么时候必须停下

主流程如下：

```text
信息收集 → 缺陷分诊 → 根因调查 → G1
        → [前端 E2E 复现] → 方案设计 → G2
        → 修复实现 → 验证 → G4 → 收尾建议 → G5
```

到达检查点时按 `confirmation-gates.md` 判断证据、范围与授权。条件满足则报告并继续；只有下一步依赖用户决定时才暂停。Jira 同步单独核对授权，未同步不阻断无依赖的已授权本地工作。

重复、无效或无需代码修复的缺陷可以从分诊直接进入收尾建议，不需要伪造中间阶段，但最终 Jira 动作仍受 `G5` 约束。

## 1. 信息收集：把问题说清楚

**目标**

建立足够开始分诊的最小事实集，而不是立刻猜根因。

**必做**

- 记录 issue key、标题、当前状态、负责人、组件和优先级。
- 提取复现步骤、期望结果、实际结果、附件和关键评论。
- 把相对时间转换为带日期和时区的绝对时间。
- 标出环境、请求或业务标识，以及仍缺失的证据。

**完成标志**

开发者能一眼看出“发生了什么、在哪里发生、什么时候发生、还缺什么”。

**停止点**

缺少环境、时间或可观察现象，导致无法缩小调查范围时，先请求最小补充信息。

## 2. 缺陷分诊：决定由谁、沿哪条链路查

**目标**

判断问题是否成立、风险多大、可能属于哪个子仓库或服务。

**必做**

- 判断严重度、用户影响和是否需要代码调查。
- 识别重复单、无效单、信息不足或无需代码修复的情况。
- 用路由、类名、topic、镜像或调用链收敛 owner，不凭仓库名称猜测。
- 记录最可能的 owner、受影响模块和当前风险。

**完成标志**

已确定调查入口，或已有充分依据建议直接收尾。

**停止点**

- owner 仍不明确时继续取证，不对多个子仓库盲目修改。
- 重复、无效或无需修复时可以跳到收尾建议，但最终 Jira 动作仍必须经过 `G5`。

## 3. 根因调查：建立可验证的因果链

**目标**

解释“什么条件触发、实际走了哪条路径、为什么产生错误、用户最终看到了什么”。

**必做**

1. 固定调查坐标：规范环境、平台原始环境、app/cluster、部署镜像或 commit、绝对时间范围。
2. 用日志证明实际执行路径，用配置和只读数据核对条件与持久化结果，用事发版本代码解释错误机制。
3. 把证据排成统一时间线：用户操作 → 入口 → 核心计算 → 下游或写入 → 后续查询或展示。
4. 区分已确认事实、假设、未知项和反证；不足两类独立证据时只称为候选根因。
5. owner 明确后运行 MR 目标检测脚本，记录目标分支、来源和置信度。

运行日志、Apollo、数据库和凭据边界按 `evidence-playbook.md` 执行。

**完成标志**

根因陈述覆盖：触发条件、实际路径、错误机制、外部或持久化结果、用户影响、证据强度和未知边界。

**停止点**

到达 `G1 根因检查`：证据足够则简述根因并继续。证据不足先自主补证；只有无法补齐且会改变修复方向的未知项才询问用户，不用人工认可代替证据。

## 4. 前端 E2E 复现：把用户可见问题变成稳定失败

仅当前端用户可感知回归、关键旅程失败或状态流转异常时执行，并且必须在 `G1` 通过之后。

**目标**

得到一个能稳定重现原症状的 failing case；暂时做不到时，明确可测性 blocker。

**必做**

- 确认现有 `data-testid`、contract、fixture 和 seed 数据是否足够。
- 明确应进入的 Playwright project、tag 和关键用户断言。
- 优先补最小 failing E2E；不能补时写清 blocker 和最小补齐建议。

**完成标志**

已有 failing E2E，或已有足够明确的 blocker 可以纳入方案设计。对外呈现按 `e2e-compact-handoff.md` 压缩。

**停止点**

复现依赖尚未授权的环境操作、缺少稳定测试接缝或无法准备测试数据时，记录 blocker 和最小补齐动作，不伪造 failing case；随后带着该边界进入方案设计。

## 5. 方案设计：明确修复与必要取舍

**目标**

基于已确认根因，给出可以实施和验证的最小修复方案。

**必做**

- 形成最小修复方案；存在实质取舍时才比较真实候选，不为满足数量制造替代方案。
- 对比改动点、收益、风险、兼容性、历史数据处理和验证方式。
- 明确推荐方案、推荐理由、回滚边界和验证矩阵。
- 前端回归要说明 failing E2E 是否存在，以及修复后的 Playwright 或 smoke 范围。

**完成标志**

开发者无需补读调查过程，就能理解每个方案会改什么、承担什么风险、如何证明有效。

**停止点**

到达 `G2 方案检查`：已获实现授权，且方案明确或最小修复恢复既有约定时，报告做法和验证范围后继续。缺少授权、存在关键方案选择或范围、契约、数据风险变化时，仅确认未决部分。

## 6. 修复实现：在已授权范围内完成最小修复

**目标**

用最小必要改动消除已确认的错误机制。

**必做**

- 只修改受影响子仓库，不夹带无关改动或父仓 submodule 指针。
- 优先补能复现原症状的回归测试；存在稳定测试接缝时再采用 red-green 验证。
- 记录真实修改点、未实现项和验证入口。
- 需要 Jira 评论、`issue move` 或 `issue assign` 时，先按 `G3` 检查具体动作授权；已有授权不重复询问，缺少授权只暂停该写入及其依赖工作。

**完成标志**

实现与已授权目标、方案和范围一致，diff 可审查，并且有明确的验证路径。

**停止点**

如果实现需要扩大范围或改变已确认方案，回到方案设计，不自行扩张。

## 7. 验证：证明原症状不再发生

**目标**

验证根因修复，而不只是证明代码能够编译。

**必做**

- 先运行最邻近的 test、lint、build 或 smoke，再按风险扩大。
- 报告具体命令、通过与失败结果、未覆盖项和环境限制。
- 有 failing E2E 时，优先确认它是否转绿，并记录所属 project/tag。
- 新证据推翻根因或验证失败时，回到根因调查。

同一相关代码、配置、依赖与环境下，已有可追溯且覆盖当前验收的通过结果可以复用。记录实际命令、结果与适用范围，不因阶段切换重复执行。修复改变了验证前提或覆盖范围时，重跑受影响检查；共享行为或集成风险变化时再扩大，不能仅凭“以前通过”沿用结果。

**完成标志**

原症状的回归证据、必要的邻近验证和残余风险都已明确。

**停止点**

到达 `G4 验证检查`：必要验证通过且覆盖当前改动时，报告结果并进入收尾。失败先在范围内调查或修复；需要改变验收、接受替代证据或新增风险时才请用户决定。始终如实保留未执行和失败项。

## 8. 收尾建议：决定关闭、观察还是退回

**目标**

把修复、验证、环境证据和残余风险压缩成可执行的 Jira 收尾建议。

**必做**

- 汇总代码改动、流水线或本地验证、目标环境 smoke、必要的数据复核和观察窗口。
- 给出关闭、继续观察或退回调查的推荐及理由。
- 准备最终 Jira 评论摘要和目标状态，但暂不写入。
- 存在代码交付时，再次检测 MR 目标分支，并与调查开始时的记录比较。

**完成标志**

至少满足：修复已完成、核心验证通过、关键结论已同步或准备同步、目标状态有明确依据。

**停止点**

到达 `G5 收尾检查`：准备好最终摘要与目标动作，核对对应授权及其条件。已有明确授权且条件满足时执行；否则请求缺失的决定。只有所需 Jira 动作实际成功后才报告 Jira 收尾完成，不能以本地验证通过代替。

## 进展与决策怎么写

先给当前结论，再按需要列出：

1. 已确认事实
2. 假设与反证
3. 未知项或缺失证据
4. 建议下一步

省略空章节，不倾倒完整日志，不把推断写成事实。检查通过时简短报告并继续；只有真正需要用户决定时，使用 `confirmation-gates.md` 的决策说明。
