# 多缺陷协调

## 何时加载

仅在输入包含两个及以上 issue key，或用户明确表达“同类 / 关联 / 重复 / 一并处理”等关系时加载。
普通单缺陷流程不要读取本文件。

## 建组前提

先为每个 issue 独立收集最小证据集，再判断是否建组。表现相似只能形成候选关系，不能直接证明共享根因。

为缺陷组记录：

- `primary_issue`：承载共享分析和完整证据的主 issue
- `related_issues`：保留各自状态、负责人和验收点的关联 issue
- `shared_root_cause`：在 G1 通过前始终标为候选
- 每个 issue 独立的验收标准、当前状态与负责人

主 issue 按以下顺序选择：

1. 用户明确指定的 issue
2. 具备总括语义或证据最完整的 issue
3. 输入中的第一个 issue，并把它标记为可调整假设

使用下表压缩缺陷关系；没有证据的单元格写“未知”，不要用共享结论填补：

| Issue | 独立表现 | 共享链路证据 | 独立验收点 | 当前状态 |
| --- | --- | --- | --- | --- |
| `<KEY>` | `<可观察现象>` | `<共同请求、状态或代码路径>` | `<该 issue 必须单独满足的结果>` | `<status / assignee>` |

到达 G1 时，若该表有助理解共享结论则直接展示；只有存在待决定事项才配合决策说明，不重复输出
调查报告与确认卡。检查点是否暂停按 `confirmation-gates.md` 判断。

## Gate 语义

- **G1 根因**：仅当证据支持同一因果链时共享 Gate；否则拆成独立流程，不再按缺陷组推进
- **G2 修复方案**：可以共享一套根因修复，但必须逐项列出每个 issue 的独立验收点
- **G3 Jira 状态**：状态和指派始终按 issue 单独判断，不执行无差别批量流转
- **G4 验证范围**：同时验证共享修复和每个 issue 的独立验收点；任一未覆盖都不能宣称整组通过
- **G5 Jira 收尾**：逐 issue 给出关闭、观察或退回结论，因为状态与关闭条件属于各自 issue

## Jira 同步范围

以下操作均要求对应 issue 和动作已有授权；共享根因或方案不能把一个 issue 的写入授权扩散到关联 issue。

| Gate | 主 issue | 关联 issue |
| --- | --- | --- |
| G1 | 回填完整根因与共享证据 | 回填主 issue 链接、关系结论和自身差异或验收点 |
| G2 | 回填完整方案与共享措施 | 仅在存在独立验收或协调要求时补充精简评论 |
| G4 | 回填完整验证范围与共享结果 | 回填该 issue 的独立验收证据和结果 |
| G5 | 回填该 issue 的最终结论并按需流转 | 每个 issue 都独立回填最终结论并按需流转 |

评论同步仍按主 Skill 的独立条件路由；仅在命中重试、恢复或结果不确定场景时，再加载评论幂等 reference。

## 拆组条件

出现以下任一情况时拆成独立缺陷流程：

- 根因或修复路径不同
- 共享修复不能覆盖全部独立验收点
- issue 之间只有时间或文案上的相似性，没有共同因果链证据

拆组后保留已收集的逐 issue 证据，不把已验证信息丢弃。
