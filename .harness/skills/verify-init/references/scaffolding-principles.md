# 脚手架产出原则

按 `frameworks-index.md` 获取与实际版本匹配的官方文档后，对已确认的缺口逐项补齐。
根项目与子项目使用同一规则，安装位置由 manifest/workspace/配置归属决定。

## 产出核对

- **依赖**：使用检测到的包管理器，在实际 owner 中安装。已声明时先核对版本与可用性，
  不重复声明到其他包；依赖存在不等于测试已就绪。
- **配置**：遵循对应版本的官方 schema。已有配置不覆盖，必要的合并差异在授权范围内落实。
- **示例**：为本次补齐的测试类型提供最小可跑示例。已有可验证的同类测试时复用，不凑示例。
- **执行入口**：沿用实际 scripts、Makefile 或原生命令；缺入口才补齐。注明工作目录和环境
  前提，不强制固定 script 名称，也不改写已有 script 的含义。
- **幂等**：每步先检查现状，已满足则跳过；已有文件按内容核对，不能仅凭存在认定配置完成。

## 项目策略

先读取适用 rules、测试文档与现有配置。以下均按项目事实和已确认要求落实：

- 测试依赖编译产物时，先执行所属项目的构建；无此依赖不追加 build。
- 覆盖率沿用已配置的统计范围与门槛。新增门槛须先确认，再写入配置；不预设固定值，
  不自动排除某类测试，不将全量覆盖率误记为变更行覆盖率。
- e2e 的执行时机、重试及截图/trace/录屏按既有策略和已确认需求设置；文档记录产物位置。
- API 测试复用适合项目的隔离方式。内存、事务回滚或独立测试环境须符合真实测试目标，
  不能因通用配方替换项目数据库语义。
- mock 边界和测试分层来自现有规则；有冲突先对齐，不另写一套“通用规则”。

配置项的技术可用性以官方文档为据；它不替代用户对项目策略的决定。

## 执行与验证

1. 提取安装、配置、示例与执行入口所需的官方信息，核对版本。
2. 对比现有文件，确定已满足项、必要增量、配置 owner 和执行目录。
3. 在已确认范围内安装或增量修改，保留用户内容。
4. 运行本次补齐项的最小验证，记录命令、目录和结果；失败则修复范围内问题或明确缺口。
5. 将已落成的执行事实同步到 docs 测试说明与共用 rules，更新 AGENTS 入口。

官方信息缺失时不编造，标明未完成项。所有文档获取途径均失败时，按 skill 的降级规则跳过
安装、config、示例和 scripts 写入，只整理本地可证实的知识、规则与验证角色。
