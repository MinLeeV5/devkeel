// harness engineering

设计环境，明确意图，构建反馈回路

Harness Engineering 是一种工程方法论：工程师不再亲手写每一行代码，而是设计让 AI Agent 高效工作的环境——通过约束、文档和反馈回路，让 Agent 进入项目就知道该怎么做。

🧭 编排 · 给 Agent 一张地图

"给 Codex 的是一张地图，而不是一本 1000 页的说明书"——把工具和流程按正确顺序组合，让 Agent 知道先做什么、后做什么。

📏 规范 · 约束是加速器

"有了约束，速度才不会下降"——通过架构边界和编码标准，让 Agent 快速交付而不跑偏。

📚 沉淀 · 代码仓库即记忆

"存储在聊天记录或人们头脑中的知识都无法被系统访问"——所有经验归档到仓库，越用越厚。

OpenAI 用 3 名工程师 + Codex，5 个月产出百万行代码。关键不是更好的 prompt，而是更好的 harness。

但现实中，大多数团队让 Agent 在没有 harness 的情况下工作……

// 现状之痛

AI Agent 协作的三大痛点

⚠️ 没想清楚就开干

需求没想清楚就让 Agent 写代码，它按自己的理解实现，反复返工。

🚧 没人检查就上线

Agent 写完代码直接合入，没人帮它把关，低质量代码悄悄堆积。

🗑 做完就忘，反复踩坑

每次对话结束就清空记忆，同样的错误换个人、换个时间又犯一遍。

核心矛盾：Agent 能力很强，但它不了解你的项目——不知道该遵守什么规范、用什么工具、走什么流程。

// 是什么

编排 · 规范 · 沉淀

DevKeel 是一个项目知识框架 CLI，解决三个问题：

编排工具

把 OpenSpec、SuperPowers 等最合适的工具组合，编排进项目工作流。不重复造轮子，只做最佳搭配。

注入规范

通过 rules、skills、agents 把团队的领域知识和编码规范注入给 Agent，让它一进项目就知道该遵守什么。

沉淀知识

每次 Agent 协作的经验——方案决策、代码审查、踩过的坑——自动归档到 openspec/，越用越厚。

.harness/ = skills + rules + agents  →  分发到 Claude Code / Cursor / Codex / Copilot

// 深度结合

流程 × 方法论 深度结合

OpenSpec

流程编排器

定义"走哪步"。管理 artifact 链和完整生命周期：brainstorm → design → specs → tasks → apply → verify → archive。每个阶段有明确的输入、输出和依赖关系。

SuperPowers

方法论工具库

定义"怎么做好"。在每个阶段注入专业 skill：requirement-analysis（5W1H/SCAMPER/MECE）、technical-design（C4/ATAM/STRIDE）、writing-plans、TDD、code-review。

OpenSpec 管"走哪步"，SuperPowers 管"怎么做好" —— DevKeel 把它们编排到一起，让每个阶段都有专业方法论支撑。

// 怎么开始 · step 2

/domain-init 为你的项目量身定制

扫描你的代码，提炼你的规范——不生搬硬套，只量身定制

①
扫描你的代码

多 Agent 并行分析：编码风格、命名约定、架构模式、错误处理

②
提炼你的规范

从实际代码中提取约定，不是套用通用模板——每条 rule 都有代码出处

③
对比业界标杆

先采样你的代码，再对比开源标杆项目，标记内部不一致的地方并推荐统一方向

④
交互式增强

自动 baseline 生成后，头脑风暴补充团队特有规范——先扩散后收拢

为什么只有量身定制才是高质量？

通用模板说"用 camelCase"——但你的项目可能文件名用 kebab-case、函数用 camelCase、常量用 UPPER_SNAKE。

domain-init 扫描后的 rule 会精确到："文件名用 kebab-case，模块级常量用 UPPER_SNAKE_CASE，函数内局部常量用 camelCase"。

这种精度，Agent 才能真正遵守。

所有产出必须经 review 确认后才写入 .harness/——代码即规范，但人类把关。

// 怎么开始 · step 3

/verify-init 搭建可执行测试基建

扫描已有框架 → 增量补齐脚手架 → 生成验证 agent，让 Agent 能自主验证代码输出

①
检测优先

扫描依赖/配置/锁文件/目录，输出就绪清单——已有框架标记「已就绪」不重复装

②
增量补齐 + 幂等

缺失项经用户勾选后安装，照官方文档产出 config/示例/scripts，已存在不覆盖

③
生成验证 agent

test-verifier：确认目标 → 识别变更范围 → 收窄 scope 跑测试 → blocker-first 回报

④
fetch 失败降级不阻塞

文档获取失败时跳过精确 config，仍产出通用 testing 规范 + agent，不凭记忆编造

搭台子 · 写剧本 · 当演员

verify-init 搭台子——框架 + 通用规范 + 执行 agent

test-case-designer 写剧本——从需求/spec 产出用例文档

验证 agent 当演员——执行测试 + 判定 + 回报

// 怎么开始 · step 4

产物概览：两个核心目录

.harness/ ← 能力配置 ├── rules/ ← 编码规范、架构约束 ├── skills/ ← 可复用的工程方法论 ├── agents/ ← Agent 角色定义 ├── commands/ ← 自定义斜杠命令 └── config.yml ← 项目配置 openspec/ ← 知识与流程 ├── config.yaml ← openspec 配置 ├── schemas/ ← 流程编排源码 ⭐ │ └── superpowers-lite/ │ └── schema.yaml ← lite 版 artifact 流程链 ├── specs/ ← 正式行为契约 ├── changes/ ← 进行中的变更 └── archive/ ← 归档的历史变更

.harness/ = 能力配置

rules 约束行为边界、skills 提供方法论、agents 定义角色——Agent 进入项目时自动加载。

openspec/schemas/ = 流程编排源码

schema.yaml 定义整条 artifact 链的顺序、依赖、执行器路由——这就是我们定制的工作流引擎代码。修改 schema 就是修改流程。

openspec/archive/ = 知识沉淀

每次变更的 brainstorm、design、spec、retrospective 完整归档，形成可检索的项目知识库。

// feature 旅程 · step 3

按需规划 — 流程仪式感与风险成正比

brainstorm 之后，根据变更规模走不同路径

轻量路径

brainstorm → tasks → apply

日常迭代、bug fix、单模块改动。不需要 design 和 specs，直接从需求到任务拆解。

架构路径

brainstorm → design → tasks

新模块、重构、多方案对比。用 technical-design（C4/ATAM/STRIDE）产出架构决策。

完整路径

brainstorm → design → specs → tasks

API 契约、跨系统集成。用 WHEN/THEN 定义精确的行为约定。

design 和 specs 不阻塞 tasks —— 即使跳过，tasks 也能从 brainstorm 中的源码调查和验收标准获取足够信息。

// feature 旅程 · step 4

任务拆解 与 人工审阅

tasks.md — 任务拆解

使用 writing-plans skill 拆解实现任务。

粗粒度 checkbox + 缩进微步骤 + commit 点。条件读取上游 artifact：brainstorm 必读，design/specs 存在则读。

①
条件读取

brainstorm 必读；design.md 存在则读架构决策；specs 存在则读 WHEN/THEN 场景

②
微任务粒度

每个粗粒度任务拆解为可独立执行的微步骤，附带 commit 点

③
TDD 输入

specs 的 WHEN/THEN 场景直接成为 TDD 的 RED 步骤输入

⚡ human-review — 可选门禁

可选 artifact：适用于大变更、多人审阅、需要向非技术成员展示方案。

生成 HTML 验收文档 → 人工 approve → 进入 apply。

Token 节省设计

Agent 只生成可变内容——Dashboard SVG、风险卡片、任务概览。

脚本注入不可变内容——CSS 样式、交互 JS、artifact 原文。通过 inject-review 命令自动完成。

/opsx:apply 执行实现

git worktree 隔离（可选）+ subagent-driven-development 逐任务派发，内置双重审查

apply 前置：git worktree 创建隔离分支（可选，推荐多模块/多人协作时使用）+ 子模块初始化（若有 .gitmodules）

每个任务由独立 agent 执行，上下文隔离互不干扰。

双重审查

每个任务完成后：spec 合规审查 + 代码质量审查。

两道门禁确保质量

零外部依赖

纯原生 Agent 能力，无需安装额外工具。

Claude Code 和 Codex CLI 统一行为

# 执行器完整流程 1. git worktree 创建隔离分支 （可选，推荐多模块/多人协作时使用） 2. submodule 初始化（若有 .gitmodules） 3. subagent-driven-development 逐任务派发 每个任务内部强制： ✔ TDD（RED → GREEN → REFACTOR） ✔ code-review（每个任务完成后审查）

// feature 旅程 · step 6

/opsx:verify 对照验证

⚡ 7 项系统化验证

不是跑一下测试就完事。verify 按 schema 定义的 7 个维度逐项对照——任何一项 FAIL 都阻塞归档。

①
结构验证

openspec validate --all 确认 artifact 格式正确

②
任务完成度

tasks.md 所有 checkbox 为 [x]，剩余 [ ] 需标注原因

③
增量 spec 同步

change/specs/ 是否已同步到 openspec/specs/

④
Design 一致性

实现是否符合 design.md 的架构决策

⑤
实现信号

测试全通过 + 无未暂存文件 + 引用提交范围

⑥
路由泄漏检测 ⚠️ 警告不阻塞

确认设计产出未落入错误目录

⑦
覆盖缺口检查 仅有 [~] 任务时

延迟验证的测试项是否有等价自动化测试覆盖

# /opsx:verify 输出 Verifying change: add-telemetry ✔ §1 结构验证 all valid ✔ §2 任务完成度 5/5 [x] ✔ §3 spec 同步 2/2 已同步 ✔ §4 design 一致性 无偏差 ✔ §5 实现信号 tests: 12 passed, 0 failed staged: 无未暂存文件 commits: 4 (abc1234..def5678) ⚠ §6 路由泄漏 未检测到 (警告不阻塞) ✔ §7 覆盖缺口 无延迟项 Overall Decision: ✅ PASS

// feature 旅程 · step 7

代码审查：requesting-code-review

SuperPowers 的 requesting-code-review 在每个任务完成后自动触发，apply 结束时执行最终整体审查。

①
任务级审查

每个 task 完成后，调度 code-reviewer subagent 检查 spec 合规性和代码质量

②
整体审查

所有任务完成后，对整体实现执行最终 review

③
Spec 合规性

对照 specs/ 中的 WHEN/THEN 验证行为是否正确实现

④
阻断优先

blocker / regression 排最前，不输出样式级 nit

# schema 中的审查编排 apply 阶段强制 skills： test-driven-development → 每个任务 RED-GREEN-REFACTOR requesting-code-review → 每个任务完成后审查 → apply 结束前最终审查 # 审查关注点 ✔ spec 合规性（行为是否匹配 WHEN/THEN） ✔ 代码质量（架构约束、命名规范） ✔ 测试覆盖（test-points 是否全覆盖） ✔ 安全性（无硬编码密钥、无注入风险） # 发现问题时 → 执行器自动修复并重新审查 → 无法自动修复时暂停，等待人工决策

// feature 旅程 · step 8

归档 与 证据化回顾

知识越用越厚

每完成一个 change，archive 就多一份完整记录。半年后 30+ archived changes = 项目知识库。

经验回流到 Rules

反复出现的问题提炼成新 rule——Agent 从此自动遵守。

新人 Onboarding

让 Agent 读一遍 archive/——比看代码注释快 10 倍理解设计决策。

retrospective — 证据化回顾

每个论断都引用 commit hash、文件路径或测试名称：

§0 证据 — 提交数、diff 规模、任务完成率、subagent 调度次数

§1 收获 / §2 不足（🔴 阻塞 / 🟡 痛点 / 📌 小问题）

§3 计划偏差 / §4 Skill 合规性 / §5 意外

§6 晋升候选 — 经验提炼为长期学习（memory / CLAUDE.md / schema）

回顾不是走过场——§4 跳过的 skill 必须回答"跳过了什么、为什么、如何防止再次发生"。
